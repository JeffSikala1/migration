🔄 Core Finish-Release Principles

Finish-release plans must be validation-first, repo-aware, artifact-aware, and idempotent.
	•	Do not guess the release branch. Always derive it from the Maven version as release/<version> by stripping -SNAPSHOT.
	•	Do not assume repository structure. Always validate the actual remote branch model before writing finalize logic.
	•	Do not assume the integration branch is main. It may be develop, main, master, or another repo-specific branch.
	•	Do not assume artifact layout. Always validate actual Artifactory group, component, classifier, packaging, and version structure before promotion logic.
	•	Do not treat cleanup as proof of release success.
	•	Do not treat ancestry reproving failure from a fresh workspace as authoritative proof that release finalization failed.

⸻

🏗️ Standard Pipeline Design

When modernizing finish-release plans, use a two-stage pattern:
	1.	Promote Release Artifacts
	2.	Finalize Git Release

Use Maven directly to resolve the current version:

mvn help:evaluate -Dexpression=project.version -DforceStdout

Avoid legacy parser tasks and avoid the Variable Extractor plugin.

Use a shared rerun-safe control variable such as bamboo_skip_release written to a properties file and injected into later tasks, so already-finalized releases can cleanly skip promotion/finalization/cleanup work.

When validating release artifacts, compare against the full expected artifact inventory for that application. Do not treat “some artifacts found” as equivalent to “release complete” when deciding whether promotion should skip.

🔁 Idempotency & Rerun Behavior

Finish-release plans must be rerun-safe and idempotent.

Common real-world sequence:
	•	artifact promotion succeeds
	•	merge succeeds
	•	tag creation succeeds
	•	release branch deletion succeeds or partially succeeds
	•	rerun occurs from a fresh workspace
	•	ancestry may not be cleanly reproven in the same way as the original run

This must not be treated as a release failure if stronger final-state signals prove completion.

Plans must be safe when rerun after:
	•	successful promotion
	•	successful merge
	•	successful tag creation
	•	already-deleted release branch
	•	already-promoted release artifacts
	•	already-existing release tag

✅ Final-State Signals (Authoritative)

The following signals are authoritative proof of release completion:
	•	remote release tag exists
	•	full expected release artifacts exist in conexus-release-local
	•	release branch is absent, or can be treated as cleanup-only

If these are true:
	•	treat the release as finalized
	•	skip promote / finalize / cleanup work as appropriate
	•	do not fail the plan solely because ancestry cannot be reproven from the current workspace

Important: when using release artifacts as a completion signal, prefer full expected artifact count rather than partial existence.

⸻

🧹 Cleanup Rules (Critical)

Cleanup is not proof of release success.

Cleanup must be:
	•	idempotent
	•	rerun-safe
	•	tolerant of already-finalized state
	•	best-effort when only cleanup remains

Cleanup should:
	•	validate remote tag existence
	•	validate integration branch existence when needed
	•	fetch only required refs
	•	delete conflicting local tags first:

git tag -d <tag> || true


	•	attempt ancestry validation when possible
	•	attempt release branch deletion when appropriate

However:
	•	cleanup must not fail the plan solely because ancestry cannot be reproven from a fresh workspace
	•	cleanup must not be treated as authoritative release validation
	•	if final-state signals are already present, cleanup failure should not invalidate the release
	•	release branch deletion should be treated as best-effort once release completion is already proven by stronger signals

If final-state signals are present:
	•	skip cleanup entirely, or
	•	perform best-effort branch deletion without failing the plan if deletion is unnecessary or already complete

⸻

🧪 Git Finalization Behavior

Git validation must be:
	•	defensive
	•	explicit
	•	repo-aware
	•	but not overly strict

Do:
	•	fetch required refs explicitly
	•	validate release branch existence before merge logic
	•	validate integration branch existence before merge logic
	•	check whether the release tag already exists
	•	verify whether the tag is contained in the integration branch when possible
	•	treat “already up to date” and “nothing to commit” as normal rerun-safe outcomes where appropriate

Do not:
	•	fail solely due to inability to re-prove ancestry
	•	rely on local workspace state as source of truth
	•	assume the branch checked out by Bamboo is the branch to finalize into

Prefer multi-signal validation over single-check logic.

🧷 Proven Finish-Release Implementation Pattern

Prefer this implementation pattern for finish-release plans:

Promote stage
	•	validate mounted SSH key
	•	write Maven settings dynamically
	•	resolve current version with Maven
	•	derive release/<version> from Maven version
	•	validate release branch existence
	•	if release branch is absent, check for final-state signals:
	•	remote tag exists
	•	full expected release artifacts exist
	•	if final-state signals exist, set skip variable and exit successfully
	•	if release branch exists, convert -RC back to -SNAPSHOT on the release branch if needed
	•	validate release repo state before promotion:
	•	0 expected artifacts found → allow promotion
	•	full expected artifacts found → skip promotion
	•	partial expected artifacts found → fail and investigate
	•	run promote.py once per validated component/artifact family

Finalize stage
	•	resolve version again independently
	•	validate release state before finalize
	•	if final-state signals already exist, set skip variable and exit successfully
	•	validate integration branch explicitly
	•	merge release branch into actual integration branch
	•	remove -SNAPSHOT from release versions if needed
	•	create and push release tag if absent
	•	push integration branch if needed
	•	treat “already up to date” and “no snapshot versions found” as normal rerun-safe outcomes
	•	handle cleanup separately from proof of release success

Cleanup
	•	if skip variable is set, exit successfully
	•	if release is already proven finalized, either:
	•	skip cleanup, or
	•	perform best-effort release branch deletion without making plan success depend on it

	•	wrong assumption about integration branch
	•	missing release/<version> branch
	•	incorrect Maven-derived version
	•	incorrect groupId / artifactId / component mapping
	•	multi-module vs single-artifact mismatch
	•	missing RC artifacts in conexus-rc-local
	•	partial release artifacts already present in conexus-release-local
	•	existing release tags
	•	rerun/idempotency behavior
	•	cleanup being treated as release validation
	•	workspace ancestry checks being treated too strictly
